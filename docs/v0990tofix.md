# v0.99.0 待修复与待改进清单

本文档记录 v0.99.0 当前确认的待修复问题与后续功能改进点。

## #1 Bug：移动端熄屏唤醒后“正在通话”状态未同步

### 类型

Bug

### 优先级

中高

### 影响平台

- Android 当前版本
- iOS 本地测试

### 不受影响平台

- 网页版本
- Win64 便携版

### 现象

移动端软件从熄屏或后台状态唤醒时，如果 FMO 当前已经有人正在通话，Dashboard 的“正在通话”区域会显示“当前无人发言”。

如果打开了“通联语音播放”，仍然可以听到语音，说明音频链路本身是正常的。

### 进一步表现

唤醒时错过的当前通话不会主动刷新到 UI。只有当当前通话结束，并且下一次通话开始时，才会重新刷出正在通话的呼号。

### 初步判断

该问题更像是移动端生命周期恢复时缺少当前通话状态同步，而不是通用 UI 渲染问题。可能原因包括：

- 移动端后台或熄屏期间错过了“通话开始 / 发言开始”实时事件；
- App 恢复前台后只恢复了语音播放链路，没有主动补拉当前通话状态；
- WebSocket 或事件订阅恢复后没有重新读取 active speaking 快照；
- “当前无人发言”状态被重置后，未被当前通话状态覆盖。

### 建议修复方向

在移动端从后台 / 熄屏恢复到前台时，主动触发一次当前通话状态同步，避免只依赖下一次实时事件刷新 UI。

重点排查：

- Capacitor `App.resume`；
- `visibilitychange`；
- WebSocket 重连后的状态补偿；
- “通联语音播放”和“正在通话 UI”是否使用不同恢复路径。

## #2 改进：Dashboard 通联列表中带星标呼号可点击打开通联卡片

### 类型

功能改进 / Dashboard 交互增强

### 优先级

中等偏高

### 需求描述

在 Dashboard 页面的通联列表中，如果出现已经通联过的呼号，也就是界面中带星标的“老朋友”呼号，应支持点击该呼号，打开对应的通联卡片 / 老朋友详情弹窗。

### 交互要求

- 只有已通联过、带星标的呼号需要可点击；
- 鼠标悬浮时提示：`查看通联卡片`；
- 不使用传统蓝色超链接字体，避免破坏 Dashboard 当前视觉风格；
- 可以保持现有呼号颜色和星标样式，只增加鼠标指针、轻微 hover 状态或下划线；
- 点击后打开该呼号对应的“老朋友”通联卡片，展示历史通联记录。

### 目标

减少用户从 Dashboard 切换到“老朋友”页面再手动搜索呼号的操作成本。值守时看到熟悉呼号，可以直接查看历史通联信息。

## #3 功能改进：增加 FMO 远程访问测试表单

### 类型

功能改进 / 远程访问辅助工具

### 背景

普通用户自行搭建 DDNS、内网穿透、FRP、反向代理等服务门槛较高。现有的 mDNS / `fmo.local` 只适用于同一局域网，不能解决外网访问家中 FMO 的问题。

如果用户具有稳定公网 IP，并在路由器上设置端口映射到 FMO 地址，也可以实现远程访问。DDNS 域名、第三方内网穿透服务同理，只要最终外部地址能够访问 FMO 的 HTTP API 和 WebSocket。

### 目标

先在 Dashboard 侧提供一个简单的“远程访问测试 / 配置助手”页面，帮助用户验证远程访问地址是否能正确连到家中的 FMO。

该功能不负责真正创建 DDNS 或内网穿透服务，只负责地址填写、拼接、测试、保存和错误提示。

### 适用场景

- 用户有稳定公网 IP；
- 用户在路由器上做了端口映射到 FMO；
- 用户使用 DDNS 域名指向家庭公网 IP；
- 用户使用第三方内网穿透服务，并拿到了外部访问地址。

### 表单字段建议

- 访问方式：公网 IP / DDNS 域名 / 内网穿透地址；
- 协议：`http` / `https`；
- 域名或 IP：例如 `example.ddns.net`、`1.2.3.4`；
- 端口号：例如 `80`、`8080`、`12345`；
- FMO 路径前缀：默认空，用于兼容反向代理路径；
- 是否测试 WebSocket / 音频流；
- 可选备注：例如“家里路由器映射 18080 -> FMO:80”。

### 测试内容建议

- 拼出完整 FMO 地址，例如 `http://example.ddns.net:18080`；
- 测试基础 HTTP API 是否可访问；
- 测试设备信息 / 当前状态接口；
- 测试 WebSocket 是否能连接；
- 如当前功能支持语音播放，可进一步测试音频流连接；
- 根据结果给出清晰提示：成功、超时、跨域错误、证书错误、接口不符合 FMO、WebSocket 失败等。

### 测试成功后的操作

可提供：

- 保存为当前 FMO 地址；
- 复制远程访问地址；
- 查看路由器端口映射提示。

### 安全提醒

页面中需要明确提示：

- 不建议把 FMO 无保护地直接暴露到公网；
- 优先使用 HTTPS、VPN、Tailscale / ZeroTier，或带鉴权的反向代理；
- 如果使用端口映射，尽量使用非默认外部端口；
- 远程控制类功能尤其需要注意访问权限。

### 长期方向

更理想的方案是 FMO 固件或官方生态统一支持 DDNS / 远程访问服务。设备侧自动注册稳定访问标识，Dashboard 侧通过呼号、设备 ID、授权码或二维码完成绑定和访问。

Dashboard 可以先实现远程地址友好配置与连接检测，未来再配合 FMO 固件的官方远程访问能力。

## #4 改进：PC 便携版启动界面不应像安装界面

### 类型

体验改进 / PC 便携版专项

### 优先级

中等

### 影响平台

- Win64 便携版

### 现象

PC 便携版启动时的界面看起来像一个安装界面，容易让用户误以为正在安装软件，或者需要进行安装流程。

### 问题

便携版的核心预期是下载后直接运行，不应给用户“安装中 / 安装向导 / 正在部署”的感觉。当前启动界面会削弱“绿色便携版”的认知，也可能让不熟悉电脑的用户犹豫是否继续操作。

### 期望表现

PC 便携版启动界面应更像应用加载界面，而不是安装界面。

建议：

- 显示 `FMO仪表盘`；
- 显示当前版本号；
- 显示简短状态，例如 `正在启动...`、`正在加载本地服务...`；
- 避免出现类似安装进度、安装器标题、解压安装、向导式布局等视觉暗示；
- 如果首次启动需要释放资源或准备运行环境，文案应使用“正在准备便携运行环境”这类表达，避免使用“安装”。

## #5 Bug：网页版和 PC 便携版呼号语音播报偶尔重复播放

### 类型

Bug

### 优先级

中等

### 影响平台

- 网页版
- Win64 便携版

### 现象

在播报呼号时，调用内置语音引擎偶尔会出现同一个呼号播放两次的情况。

### 初步判断

该问题可能不是单纯的语音引擎问题，更像是播报触发链路偶发重复触发。

可能原因包括：

- 同一条发言事件被处理了两次；
- WebSocket 重连或轮询刷新时重复触发播报；
- speaking 状态变化时 watcher / store action 重复调用；
- PC 便携版和网页版共用 web 平台路径，因此两者同时出现；
- 去重逻辑只针对显示层，没有覆盖语音播报层；
- 同一呼号在很短时间内连续收到两次状态更新，被误判为两次新播报。

### 期望表现

同一次发言或同一条通话事件，只应触发一次呼号播报。即使短时间内收到重复事件，也应有防抖 / 去重保护。

### 建议修复方向

- 在语音播报入口增加短时间去重；
- 按 `callsign + addressId + speakingStartTime` 或事件 ID 做去重；
- 没有事件 ID 时，可设置 1-3 秒的同呼号去重窗口；
- 检查 Dashboard / SpeakingBar / store 是否存在重复监听；
- 检查 WebSocket 恢复或轮询补偿是否会重复派发同一发言状态。

## #6 Bug：网页版和 PC 便携版进入应用时偶尔未显示当前通联

### 类型

Bug

### 优先级

中高

### 影响平台

- 网页版
- Win64 便携版

### 现象

偶尔在进入网页版或 PC 便携版时，如果 FMO 当前正在通联，发言框仍显示“无人通联”。

### 与 #1 的关系

该问题与 #1“移动端熄屏唤醒后正在通话状态未同步”相似，但触发场景不同：

- #1：移动端熄屏 / 后台唤醒时错过当前通话状态；
- #6：网页版或 PC 便携版首次进入 / 重新打开应用时，偶尔没有正确同步当前通话状态。

两者可能共享部分根因：应用只依赖实时事件刷新“正在通话”状态，而没有在启动、恢复或连接成功后稳定拉取当前 active speaking 状态。

### 初步判断

可能原因包括：

- 页面初始化时 WebSocket 尚未收到当前通话快照；
- 当前发言已经开始，但前端只监听后续“开始发言”事件；
- 初始化阶段状态接口和实时事件存在竞态；
- “无人通联”默认状态先显示后没有被当前状态覆盖；
- PC 便携版和网页版共用 web 平台逻辑，因此两个平台都有偶发现象。

### 期望表现

打开应用时，如果 FMO 当前已经有人正在通联，应能稳定显示当前发言呼号，而不是等待下一次通联事件。

### 建议修复方向

- 应用启动时主动拉取一次当前通话 / 当前发言状态；
- WebSocket 连接成功后主动补一次当前 speaking 快照；
- 状态接口返回前避免过早确认“无人通联”；
- 对“无人通联”增加加载 / 未确认状态，减少误导；
- 与移动端恢复前台同步逻辑合并设计，形成统一的“状态补偿刷新”。

## #7 Bug：使用 `fmo.local` 作为 FMO 地址后刷新和全量同步可能失败

### 类型

Bug

### 优先级

中高

### 已发现平台

- 网页版
- Win64 便携版

### 待确认平台

- Android

### 暂未复现平台

- iOS 测试环境

### 现象

在设置页面添加 FMO 地址时，如果直接选择或填写 `fmo.local`，后续再次打开应用后，可能出现：

- 刷新不成功；
- 全量同步日志不成功；
- FMO 连接状态异常或接口请求失败。

### 初步判断

该问题可能与 `fmo.local` 的 mDNS 解析、地址规范化、缓存保存方式或跨平台访问路径有关。

可能原因包括：

- `fmo.local` 在浏览器 / PC 便携运行环境中偶尔解析失败；
- 再次打开后保存的地址没有补全协议，例如 `http://fmo.local`；
- 地址规范化逻辑对 `.local` 域名处理不一致；
- 同步接口和实时刷新接口使用了不同的地址拼接逻辑；
- mDNS 解析结果有缓存或超时问题；
- PC 便携版 WebView / 系统 DNS 对 `fmo.local` 支持不稳定；
- 如果网页部署在 HTTPS 下访问 `http://fmo.local`，可能触发混合内容或私有网络访问限制。

### 期望表现

选择 `fmo.local` 后，应用应稳定保存并使用正确地址。重新打开后，刷新和全量同步日志都应正常工作。

### 建议修复方向

- 检查设置页保存 FMO 地址时是否统一规范化为完整 URL；
- 对 `fmo.local` 做专门处理和连接测试；
- 保存时记录用户原始输入和规范化后的实际访问地址；
- 刷新、同步、WebSocket、日志备份等功能统一使用同一个地址解析工具；
- 如果 `fmo.local` 解析失败，提示用户改用 FMO 的局域网 IP；
- 在连接测试结果中区分 DNS 解析失败、超时、接口不可达、跨域 / 安全限制；
- 进一步验证 Android / iOS 是否也会受影响。

## 修复时机

以上问题计划作为 iOS 发包前的集中修复与验证清单。优先处理会影响实时通联状态、FMO 地址连接、日志同步和语音播报准确性的项目。

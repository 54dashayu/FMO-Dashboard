### #1 FMO 频率有 TX/RX 之分，Dashboard 频率显示需要重新布局

#### 类型

Bug / 数据展示修正 / UI 布局优化

#### 优先级

高

#### 影响平台

- Web V2
- Android
- iOS
- Windows 桌面版
- macOS 桌面版

#### 现象

Dashboard 第一屏“频率 / 模式”卡片目前按单一频率展示，只显示一个 `freqHz` 或只显示 `FMO` 模式。

但 FMO 中继/频率实际存在 TX、RX 区分，尤其在异频配置时，单一频率显示会造成信息不完整，用户无法直观看到收发频率。

#### 影响

- 异频中继时，用户无法确认当前 TX/RX 是否正确。
- 频率卡片容易被误解为只有一个工作频率。
- 后续如果用于车机/移动首屏，信息不准确会影响值守判断。

#### 初步判断

当前 Dashboard 的实现把频率和模式压缩为一个字符串，优先读取通联日志里的 `freqHz`，没有 TX/RX 结构化展示。

TX/RX 数据可能来自：

- `station:getCurrent`
- `station:getListRange`
- `qso:getDetail`
- 后续 FMO 协议新增字段

字段名尚需用真实 FMO 异频配置返回值确认。

#### 期望表现

如果接口返回 TX/RX 字段，频率卡片应显示：

```text
TX  xxx.xxxx MHz
RX  xxx.xxxx MHz
模式 FMO
```

如果旧数据只有单一频率，则降级显示：

```text
频率 xxx.xxxx MHz
模式 FMO
```

如果没有任何频率字段，则显示：

```text
模式 FMO
```

### #2 设置 FMO 地址后，全量同步数据过多时容易同步失败

#### 类型

Bug / 同步机制稳定性 / 大数据量兼容

#### 优先级

高

#### 影响平台

- Web V2
- Android
- iOS
- Windows 桌面版
- macOS 桌面版

#### 现象

设置 FMO 地址后，如果执行全量同步，数据量较多时容易同步不成功。表现可能包括：

- 同步长时间卡住。
- 中途请求超时。
- 部分记录失败较多。
- WebSocket 连接断开后没有很好恢复。
- 本地数据库写入节奏过慢，导致整体同步耗时过长。

#### 影响

- 新用户首次配置 FMO 地址时体验差。
- 历史日志较多的用户难以完成初次同步。
- 多地址同步或全量同步时失败概率增加。
- 用户可能误以为 FMO 地址配置错误。

#### 初步判断

当前全量同步流程是：

1. 分页拉取 QSO 列表。
2. 对每条记录逐条请求 `qso:getDetail`。
3. 每条详情请求后单条写入 IndexedDB。
4. 长时间复用同一个 WebSocket client。

数据量大时，问题可能来自：

- 单条详情请求过多，耗时长。
- 每条记录单独写 IndexedDB，事务数量过多。
- 单个 WebSocket 连接长时间工作后不稳定。
- 列表/详情请求超时时间偏短。
- 页面刷新或后台任务与手动同步之间存在竞态。

#### 期望表现

- 大数据量全量同步应能稳定完成。
- 单条详情失败不应导致整个同步立刻失败。
- 页面应显示可理解的进度。
- 长同步过程中可周期性释放/重建连接。
- 数据库写入应批量化，减少事务开销。

#### 2026-06-14 本地修复记录

已初步修改：

- `src/core/sync/syncEngine.ts`
  - 全量同步页大小从 20 调整为 50。
  - 页内详情先缓冲，整页批量保存。
  - 详情请求间隔从 100ms 调整为 60ms。
  - 页间等待 250ms。
  - 每 8 页主动关闭 client，下次请求自动重连，降低长连接失败概率。
  - 同步状态文案显示页内进度和已同步数量。
- `src/services/db.js`
  - 新增 `saveQsoBatchToIndexedDB(records)`。
  - 按 `fromCallsign` 分组批量写入，减少 IndexedDB 事务数量。
- `src/services/fmoApi.js`
  - `qso:getList` 和 `qso:getDetail` 请求重试从 1 次增加到 2 次。
  - 请求超时从 12 秒放宽到 18 秒。

已验证：

- 修改文件聚焦 ESLint 通过。
- `npm run typecheck` 通过。
- `npm run build` 通过。
- `git diff --check` 通过。

- 记录失败时的具体错误文案和失败 logId 数量。
- 如仍失败，下一步考虑：
  - 增加同步任务断点续传。
  - 将全量同步拆成“列表索引同步 + 详情补齐”两阶段。
  - 对详情请求做有限并发，但必须先确认 FMO WebSocket 协议是否允许同类请求并发。

### #3 Android 老版本系统适配：车机、老手机、鸿蒙等 Android 10 以下环境

#### 类型

兼容性改进 / Android 适配 / 车机场景支持

#### 优先级

中高

#### 影响平台

- Android
- 车机 Android 系统
- 老手机 Android 系统
- 华为 / 荣耀鸿蒙兼容层

#### 现象

V2.0 后续需要关注 Android 老版本系统适配。部分车机、老手机、鸿蒙系统设备的 Android 版本可能在 Android 10.0 以下，实际运行环境可能明显落后于主流手机。

当前工程配置：

```text
minSdkVersion = 24
compileSdkVersion = 36
targetSdkVersion = 36
```

这意味着 APK 理论上允许安装到 Android 7.0 及以上设备，但实际能否稳定运行，还取决于：

- 系统 WebView / Chrome WebView 版本；
- Capacitor Android 与 AndroidX 依赖的兼容性；
- 厂商 ROM 或鸿蒙兼容层的 WebView、权限、后台服务限制；
- 车机系统是否缺少现代浏览器组件；
- 音频播放、后台服务、通知、定位等原生插件在旧系统上的行为；
- 老设备 CPU、内存、存储性能对 V2 页面和同步任务的承载能力。

#### 影响

- 部分老车机可能无法启动、白屏、闪退或 WebView 功能缺失。
- 老手机可能安装成功但连接 FMO、同步、语音播报或后台保活异常。
- 鸿蒙兼容层可能出现权限、WebView、音频或后台服务行为差异。
- 用户可能误以为 V2 Android 包本身损坏。

#### 初步判断

需要把“理论 minSdk 支持”和“实际设备可用”分开处理。

V2.0 当前不应盲目承诺所有 Android 10 以下设备都稳定支持，应先建立兼容性分级：

- **主支持**：Android 10 及以上主流手机 / 平板。
- **尽量兼容**：Android 8-9 老手机、主流车机。
- **有限兼容**：Android 7、厂商深度定制车机、老鸿蒙兼容层。
- **不主动支持**：缺少可更新 WebView、系统组件严重残缺或无法提供崩溃日志的设备。

#### 期望表现

- Android 10 以下设备若能安装，应尽量完成启动、配置 FMO 地址、连接、查看 Dashboard、同步最近数据等核心路径。
- 如果设备 WebView 或系统能力不足，应给出更明确的提示，而不是静默白屏或闪退。
- 对车机应额外关注横屏、低分辨率、触控目标、字体大小和滚动行为。

#### 建议修复方向

- 建立 Android 兼容性测试矩阵：
  - Android 7 / 8 / 9 / 10；
  - 典型车机横屏；
  - 华为 / 荣耀鸿蒙兼容层；
  - 低内存或低性能设备。
- 收集旧设备启动失败时的 `adb logcat`：
  - JS runtime error；
  - WebView 初始化错误；
  - 原生插件崩溃；
  - 权限或后台服务异常。
- 增加启动诊断：
  - 检测 WebView / user agent / Android 版本；
  - 记录到诊断日志；
  - 必要时显示“当前系统 WebView 过旧，请升级 Android System WebView 或 Chrome”的提示。
- 检查前端语法与构建目标是否对旧 WebView 友好。
- 检查 Capacitor / AndroidX / 原生插件最低系统要求，避免引入只在高版本系统稳定的 API。
- 对车机横屏和窄高度屏幕做单独布局回归。
- 若某些设备无法低成本兼容，应在下载页或 release notes 中标注兼容风险。
